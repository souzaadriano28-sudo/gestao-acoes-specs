## Context

See `proposal.md` for motivation. The Spring Boot 4.0.6/Java 17 backend currently defaults to the `test` profile, keeps PostgreSQL URL and user fixed in `application-dev.properties`, requires only `DB_PASSWORD`, and already accepts external provider tokens and endpoint overrides. H2 and embedded PostgreSQL tests let Hibernate create and drop the schema. Two PostgreSQL-only scripts under `db/stabilization` preflight and normalize legacy data, but they are executed manually from a test and are not a schema history.

The persistent model consists of `acao`, `corretora`, `transacao`, and `posicao_carteira`. Its constraints protect canonical identifiers, positive quantities/prices, `numeric(19,8)` monetary storage, foreign keys, and one position per action/broker. PostgreSQL row locks and transactional tests protect concurrent trading. Existing OpenSpec contracts, Maven/Angular workflows, and the isolated Playwright journey are controlling constraints.

## Goals / Non-Goals

**Goals:**

- Make local, test, container, and future deployed configuration explicit and fail-fast without storing secrets.
- Establish one reviewed schema history that works for fresh H2/PostgreSQL databases and safely adopts existing PostgreSQL data.
- Package the Angular frontend, Spring Boot backend, and PostgreSQL 17 in a reproducible, observable local composition.
- Preserve business/API behavior and prove compatibility through the current test layers plus migration and container checks.

**Non-Goals:**

- Adding an orchestrator beyond Docker Compose, registry publication, TLS, production deployment, or choosing a cloud secret manager.
- Changing entities, endpoint contracts, monetary policy, canonicalization, transaction boundaries, locking behavior or provider selection. Frontend API calls change only from an absolute development URL to the equivalent relative `/api` contract.
- Creating a real `.env`, embedding demonstration investment records, replacing H2/PostgreSQL tests, or enabling real provider traffic in automated tests.

## Decisions

### 1. Deliver three gated phases in dependency order

Phase 1 establishes the configuration contract and secret hygiene. Phase 2 consumes that contract for datasource configuration and makes migrations authoritative. Phase 3 packages exactly the already-migrated runtime. Each phase must pass its own focused tests and the pre-existing regression suite before the next begins.

Implementing all concerns at once was rejected because a startup failure would be difficult to attribute among binding, schema, and container networking.

### 2. Use Spring external configuration, not an application dotenv loader

`SPRING_PROFILES_ACTIVE`, `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `BRAPI_TOKEN`, `TWELVEDATA_API_KEY`, the four `INTEGRATIONS_*_URL` values, CORS origin, and applicable host ports form the documented contract. Secret fields have no functional default. Non-secret localhost defaults may remain only where safe. Typed configuration with validation centralizes blank-value rejection; test profiles supply explicit fake values.

The backend will version `.env.example` with empty or unmistakably nonfunctional placeholders, ignore `.env` and `.env.*` while re-including the example, and document that Spring does not read `.env` automatically. Compose may use the local file for interpolation; IDEs and shells must export it themselves. Adding a dotenv dependency was rejected as unnecessary behavior and a second configuration-loading model.

### 3. Use Liquibase as the sole schema writer and Hibernate as verifier

Add `liquibase-core` without an explicit version so Spring Boot dependency management selects the compatible release. A master changelog will include an initial portable schema for all four tables, followed only by immutable incremental changesets. Liquibase runs before JPA; every supported application/test profile uses `spring.jpa.hibernate.ddl-auto=validate` and never `create`, `create-drop`, `update`, or `none` as a substitute for the changelog.

The initial changelog is derived from the actual annotations and stabilized PostgreSQL invariants, not from the professor's sample domain. It must explicitly name primary/foreign/unique/check constraints and preserve identity generation, string lengths, timestamp/nullability decisions, enum storage, and decimal precision. A schema snapshot generated by a tool may assist comparison but cannot be accepted without entity- and SQL-level review.

Flyway was rejected because the existing `V001`/`V002` names are standalone operational scripts rather than an installed Flyway history, and introducing two migration engines would create ambiguous ownership.

### 4. Separate fresh installation from adoption of an existing PostgreSQL database

Fresh H2 and PostgreSQL databases run the master changelog normally. Existing Hibernate-created PostgreSQL databases follow a documented administrative runbook:

1. take and restore-test a backup;
2. run the existing read-only preflight with stop-on-error;
3. resolve collisions or invalid financial data explicitly;
4. apply the reviewed normalization/constraint operation once inside a transaction;
5. compare the resulting schema to the initial changelog, including names, types, nullability, indexes, foreign keys, and checks;
6. only then run `changelog-sync` for the initial baseline and start the application with Hibernate validation.

The intent of `db/stabilization/V001__preflight.sql` and `V002__normalize_and_constrain.sql` will be preserved under unambiguous adoption-oriented names and documentation. They will not also be included in normal fresh-database migrations, preventing double execution. Their current test becomes a migration-adoption test rather than an ad hoc script runner.

Automatically using `baseline-on-migrate`, swallowing "already exists", or running `changelog-sync` without equivalence proof was rejected because each can certify a divergent financial schema.

### 5. Treat rollback according to data reversibility

Reversible structural changesets declare and test explicit rollback. The initial schema may be rolled back only in a disposable database, dropping dependent objects in reverse order. Canonicalization and constraint hardening are not given a misleading automated rollback because the original spelling/format can be lost; recovery for a persistent adopted database is restore from the tested backup, followed by verification. Every future destructive migration must state its recovery class before execution.

### 6. Keep one changelog contract while isolating database-specific adoption logic

H2 and PostgreSQL both execute the common initial changelog and pass Hibernate validation. PostgreSQL-specific legacy inspection, regular expressions, temporary functions, trigger behavior, and lock tests stay explicitly PostgreSQL-only. This preserves fast H2 feedback without pretending H2 proves PostgreSQL concurrency or dialect behavior.

Using separate unrelated schemas per test engine was rejected because it would allow mappings and constraints to drift silently.

### 7. Build separate multi-stage, non-root frontend and backend images

The backend Dockerfile uses explicit Java 17 builder/runtime images, the repository's Maven Wrapper, dependency-first layering, and a final image containing the application artifact rather than source or Maven. The frontend Dockerfile builds Angular in a Node build stage and copies only the production browser assets into an unprivileged Nginx runtime. Base versions are explicit and their reviewed digests are recorded after verifying the target architecture. Both runtimes use non-root identities. Each repository has a `.dockerignore` excluding VCS, IDE, local build/test outputs, reports, and every local environment file.

Nginx listens on an unprivileged internal port, falls back to `index.html` for Angular client routes, proxies `/api` to the backend service by its Compose hostname, and exposes a lightweight health endpoint. Angular uses relative `/api` URLs in every environment; local `ng serve` uses an Angular proxy configuration to preserve the same browser contract without CORS coupling.

### 8. Compose models readiness, persistence, and least exposure

`compose.yaml` declares `frontend`, `backend`, and `postgres` on one internal application network. The backend connects to `postgres:5432`, never container-local `localhost`; Nginx connects to `backend` on its internal application port. PostgreSQL uses an explicit PostgreSQL 17 image, a named volume, and `pg_isready`; the backend depends on database health, and the frontend depends on backend health. The backend exposes a dedicated aggregate Spring health endpoint without sensitive actuator details, while the frontend healthcheck verifies Nginx locally.

The frontend is the normal host entry point and is loopback-bound on a configurable port. Backend and PostgreSQL host publications are optional, loopback-bound diagnostic/test profiles rather than requirements for browser traffic; internal service ports remain fixed and documented. Required secrets use Compose required-variable expressions; defaults are limited to non-secret database name/user and ports. `docker compose config` is validated without persisting its resolved output.

### 9. Acceptance combines existing regressions with migration/container evidence

The implementation must retain `mvnw verify`, the dedicated PostgreSQL concurrency suite, frontend tests/build, real Angular/Spring E2E with local provider stub, and strict OpenSpec/workflow checks. New tests verify fresh migration, second-start idempotence, checksum behavior, schema validation, adoption refusal/success, reversible rollback, container health, migration history, and volume persistence.

The container journey validates all three healthchecks, browser entry through Nginx, direct backend diagnostics when explicitly published, migration tables, deep-link SPA fallback, `/api` proxying, restart, and persisted investment-domain records without external provider traffic. The existing Playwright journey is pointed at the containerized frontend and uses deterministic fictitious/provider-independent data paths; if its existing provider stub is required, it stays an isolated test dependency outside the three production runtime services.

## Risks / Trade-offs

- [Existing PostgreSQL schema may differ from both annotations and stabilization SQL] → inventory every object, block baseline on any difference, and require backup plus explicit reconciliation.
- [Canonicalization is lossy and constraints can reject legacy holdings] → keep preflight read-only, identify exact rows, require a human decision, and use backup restoration rather than fictitious rollback.
- [H2 accepts syntax or semantics differently from PostgreSQL] → keep common changes portable, isolate PostgreSQL adoption logic, and require both suites.
- [Liquibase startup locks can delay concurrent application replicas] → retain the Liquibase lock, bound startup/health timeouts, and document safe lock diagnosis without manual deletion during an active migration.
- [Switching tests from `create-drop` to migration exposes hidden naming differences] → compare every JPA mapping and use `validate`; fix changelogs/entities coherently rather than relaxing validation.
- [Compose interpolation and diagnostic output can reveal secrets] → never commit rendered configuration, redact logs, use nonfunctional examples, and document secure inspection.
- [Mutable image tags weaken reproducibility] → select supported explicit versions and pin reviewed digests, with a documented refresh process.
- [PostgreSQL volume retains its original password after `.env` changes] → document SQL credential rotation versus destructive volume reset and never imply that editing `.env` rotates stored credentials.
- [Additional migration/container gates increase execution time] → preserve fast H2 tests, isolate slower PostgreSQL/container suites, and keep existing workflow timeouts under review rather than silently skipping coverage.
- [Health endpoint could disclose internals] → expose only aggregate readiness/liveness needed by Compose and keep details disabled.
- [Nginx proxy or SPA fallback can mask backend failures or static-file misses] → give health and `/api` locations precedence over the SPA fallback and test deep links, proxy failures, and backend readiness separately.
- [Relative API URLs can break local development] → make `/api` the single browser contract and supply a checked-in Angular development proxy targeting the local backend.

## Migration Plan

1. Complete Phase 1, verify ignored files and fail-fast configuration across `test`, `dev`, and PostgreSQL-test profiles, then run all existing backend and E2E checks.
2. Inventory a Hibernate-created PostgreSQL schema and the four entity mappings; produce/review the initial changelog and adoption scripts before enabling Liquibase.
3. Prove fresh H2 and PostgreSQL creation, idempotent restart, ORM validation, migration rollback, and all existing transaction/concurrency behavior.
4. Rehearse the existing-database runbook against a disposable copy: backup/restore, failing and passing preflight, one-time normalization, exact schema comparison, `changelog-sync`, restart, and data/ID preservation.
5. Build and inspect the frontend and backend images, validate the three-service Compose model with secrets supplied outside Git, start an isolated new PostgreSQL 17 volume, and wait for all three healthchecks.
6. Exercise the browser entry point, SPA deep links, Nginx `/api` proxy, optional loopback diagnostics, Liquibase history, and representative persistence across `down`/`up` without volume removal.
7. Run backend verification, frontend unit/build/audit, Playwright E2E against the containerized environment, static workflow checks, and strict OpenSpec validation; record versions, commands, timings, and platform-specific limitations, then clean only disposable resources created for this validation.

For a failed reversible changeset in a disposable environment, run its tested Liquibase rollback. For an adopted persistent database after a lossy operation, stop application traffic and restore the verified backup; do not clear checksums, remove locks blindly, or switch Hibernate back to schema mutation.

## Open Questions

- PostgreSQL 17 is the approved compatibility target. The current embedded regression fixture supplies PostgreSQL 14.15, so a dedicated PostgreSQL 17 execution remains required before production use and before selecting the Phase 3 image digest.
- The deployment platform and production secret manager are intentionally out of scope. This change defines the environment-variable boundary; platform-native injection, access control, audit, and rotation remain the deployment team's responsibility.
- No representative persistent database snapshot is present in the workspace. The adoption path can be automated against fixtures, but a real database must complete the same inventory and backup rehearsal before migration.
- Remote runners' Docker availability and acceptable added runtime are unknown. Container acceptance is mandatory locally; changing the existing required workflow requires separate evidence that it fits permissions and timeout budgets.
